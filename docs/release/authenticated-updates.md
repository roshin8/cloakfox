# Authenticated update release inputs

Development builds still disable browser updates. None of these tools turns on a network updater in an existing profile. Production activation requires an owner-controlled HTTPS host, two distinct RSA MAR certificates and the corresponding signing key in an NSS database, a Google Safe Browsing provider key, and (macOS) an Apple Developer ID Application identity/Team ID. No production credentials or trust roots are checked in.

`python3 scripts/release_config.py --help` configures an **isolated disposable patched source tree**. It checks certificates and their remaining lifetime, rejects upstream/test certificates already bundled in that tree, requires a mode-0600 provider key file, installs the two public certificates, pins the owner HTTPS host into Firefox's `application.ini`, enables the native updater with mandatory MAR verification, and uses only `cloakfox-release` MAR channels. The provider key is read by Firefox's native `--with-google-safebrowsing-api-keyfile` option; its content is not put in the command line or receipt. Like all browser API keys it is embedded in the resulting binary and is not a secret from the binary's users. Restrict its API/quota at the provider.

For macOS supply `--mac-team-id` and `--mac-signing-identity 'Developer ID Application: OWNER (TEAMID)'`. The native configure patch pins the owner Team ID for the browser/updater privileged-helper requirements while retaining Apple Developer ID certificate requirements. Mozilla's Team ID and generic/ad-hoc signing are rejected by the preparer. The owner must codesign the app and nested helpers with that identity and notarize the resulting distribution; the existing development packaging job's ad-hoc signature is **not release signing**. Windows preparation remains blocked until Authenticode ownership is integrated.

After building, create a **complete MAR** with upstream `tools/update-packaging/make_full_update.sh` from the finalized signed application (MAR is not a DMG or tarball). `python3 scripts/release_update.py --help` signs this MAR using the owner NSS key, independently verifies it against the supplied public certificate, rejects a different embedded channel/version, and writes a Firefox-native HTTPS `update.xml` with SHA-512. Use the `nss` verifier backend on Linux and `system` for the standard macOS signmar build. The tool neither uploads nor installs. Host the XML on the exact `/update/6/.../update.xml` route baked into the application; route by build target/channel/version and serve no update for an equal or newer build. Keep monotonic build IDs. Firefox's native updater additionally enforces signed MAR channel/version acceptance. Complete signed/tampered/wrong-key/downgrade and interrupted-update browser probes are release activation requirements, not established results of the local Python tests.

`python3 scripts/release_security.py` fetches Mozilla's official product-details feed and fails if the pinned engine is unknown, not latest stable, in the future, over 42 days old, or the feed cannot be checked. The tag-release job runs this gate before creating even a draft release. A daily workflow exposes rebase failures as CI failures. `--fixture` is only for offline tests and cannot authorize a release: its receipt always has `ready: false` and `testOnly: true`. `assessed_ready` records the fixture assessment; exit status 0 means that test assessment passed, not that a release is authorized. Production workflows must omit `--fixture`. This is a freshness check, not proof that every downstream native security patch is correct.

The about:cloakfox provider status checks actual classifier database table state, required Google phishing/malware lists and successful provider update age. Missing keys, missing lists, stale downloads and DB failures are separate states. It does not make a test network request or expose the key. `about:url-classifier` remains the detailed provider diagnostic. Real successful provider downloads cannot be certified until the owner provides a working key.

Local evidence: production release-metadata signature verification tests use ephemeral RSA keys; release preparation tests use ephemeral DER certificates and private test-only provider files; list readiness and XML validation use fixtures. Native MAR signing/install and owner code-signing have not run because those tools/credentials are not available in this checkout. The native Team ID function is tested from its actual source. Do not label this build production-update ready.
