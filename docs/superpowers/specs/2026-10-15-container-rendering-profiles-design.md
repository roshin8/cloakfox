# Container-owned rendering profiles

Status: requirements revised at the user's request on 2026-10-15. This supersedes the shared-cohort proposal in the recognition-warning investigation. No product implementation or installed setting changes are part of this plan update.

## Required behavior

User clarification: Apple, Intel, AMD and NVIDIA persona support is mandatory. A SwiftShader-only implementation does not satisfy this request. This is an execution requirement, not permission to relabel the existing software backend.

- Rendering profiles remain separately owned by each container. Never use a process-global selected profile, ambient container 0, or one shared profile as a fallback.
- Preserve deterministic top-level schemeful-site isolation inside each container. Reloads and restarts retain the same existing identity; generating a new persona is the explicit rotation action.
- Profiles must be compatible with the saved BrowserForge persona: selected OS, hardware family, browser identity, display and font choices. BrowserForge samples plausible identities; it does not provide GPU emulation or prove that native validation supports its claims.
- Keep the feature optional and off by default. Turning it off restores existing protected behavior, never native unmasked rendering. Retain the separate existing canvas/GPU protection controls and their current values.
- Do not weaken privacy to reduce detector warnings: preserve host-font restrictions, GPU identity protection, permission checks, readback guards, provenance, storage/network isolation and fail-closed behavior.
- macOS arm64 installed testing is the current runtime scope. Do not claim cross-platform pixel equality.

## Ownership and identity

The persistent container record owns the selected rendering-profile descriptor and its version; its values are selected using that container's existing secret and saved BrowserForge persona. Runtime presentation additionally derives from the current top-level schemeful site using existing ownership machinery. Descriptors and keys remain privileged; never expose a unique profile identifier to pages.

Different containers must have independent records, selections and secrets. They must not be silently collapsed to a single effective profile. Separation tests use deliberately identical BrowserForge persona inputs in two containers, so merely obtaining different random personas cannot hide shared state. Some standard values necessarily coincide (e.g. an API enum or supported texture limit); requiring every query to return a unique value would create invalid/inconsistent APIs. The acceptance criterion is independently owned profiles and separated identity-bearing output, with legitimate common values documented.

Existing saved seeds, personas and manual overrides must not be regenerated by enabling/disabling the feature. Invalid or stale records must not resolve to another container's record. Runtime contexts capture their owner and policy at creation; transfer/restoration must not rebind them to whichever tab is active. Incompatible active contexts require reload/recreation, not in-place mixed profile results.

## BrowserForge compatibility

A privileged compatibility validator evaluates a proposed descriptor against the complete effective persona, native backend enforcement and required privacy controls before committing it. Manual overrides participate in validation too. While the mode is active, persona generation and manual edits must validate transactionally before replacing the current record; a rejected change leaves the prior persona/profile active. Return an explicit incompatibility reason instead of replacing GPU/OS fields, clearing overrides, re-sampling the persona or substituting a shared software identity.

Compatibility does not mean attaching an Apple/Intel/NVIDIA name to a generic driver. A hardware claim requires demonstrated enforcement/emulation of the entire claimed observable profile. If a persona's hardware family cannot be supported, reject the new mode for that persona and preserve its prior protected state. The current software renderer is a rendering mechanism that may be shared internally; its context policy, resources, caches and page-visible profile must remain owner-scoped. A shared implementation must never imply a shared identity.

## Toggle

Proposed new preference: `cloakfox.opt.container_rendering_profiles`, false by default, with a Settings label “Use container-specific rendering profiles.” This is a policy opt-in, not a global profile selector. Keep `cloakfox.experimental.canvas_pipeline` and `cloakfox.opt.gpu_backend_profiles` intact; do not silently enable them or remove their guards.

Before activation, validate dependencies and all affected persisted container records. If required backend coverage is unavailable or any persona is incompatible, leave activation off, preserve all previous settings/records and explain which dependency or persona failed. Never partially switch containers under a global toggle. Store selection separately from activation so disabling/re-enabling does not rotate identity. Reload pages and restart workers to use changed policy; existing contexts retain their captured policy until destroyed. Master-off behavior remains native as before.

## Geometry implementation boundary

Replace return-value jitter only after protected layout inputs are enforced for the entire supported geometry surface. Font selection/metrics, intrinsic content, system controls, zoom, transforms, SVG, Element/Range bounds, carets and offsets must agree with actual rendered layout. Preserve per-container/site variation on identity-bearing inputs without arbitrary getter discrepancies. No CreepJS-specific element/style recognition and no unmasked fallback for text or unsupported geometry.

An authored fixed-size rectangle can legitimately be identical across profiles. Its exact engine-reference value must not require disabling protection on font-dependent or intrinsic layout. The implementation must demonstrate the distinction through general layout behavior, not a detector exception.

## GPU implementation boundary

Each proposed GPU descriptor includes the coherent capability limits, precision, extension requirements and renderer identity that its context actually enforces. Apply it to context creation, allocation/resource checks, shader translation, enum validation, WebGL1/2 shared limits, workers, WebGPU where enabled and restoration. Never advertise capacities above the enforcing backend or loosen unknown-input/readback guards. An incomplete or unsupported descriptor cannot become active.

A finite set of supported hardware/capability families is not a globally shared profile. Independently seeded presentation and owned contexts still require separation tests; cap scalar coincidences alone do not imply a link. If all protected outputs collapse across containers, reject the implementation.

## CreepJS warnings

The objective is to remove real contradictions and reduce avoidable warnings; keeping warnings is not a feature requirement. Nor can zero warnings be promised as a privacy guarantee. The pinned detector accepts one exact Gecko rotated-rectangle hash and fixed lists of GPU capability hashes. Valid protected profiles outside those lists may still trigger warnings. Do not return native values, impersonate unsupported hardware, alter a parameter to collide with a checksum, or modify detector source simply to satisfy those lists.

Report warnings verbatim with affected mode/persona, their exact predicate and whether any real identity leak or API invariant failure is demonstrated. A genuine inconsistency blocks release; an allowlist-only warning is an explicit remaining limitation for user review. The new mode must not be described as eliminating warnings until unmodified installed-browser runs confirm it.

## Verification and release gates

Use identical personas in at least two actual containers plus default; include two top-level sites, reloads, browser restart, two tabs opened concurrently, blank frames, dedicated/shared workers where supported, transfers and context loss/restoration. Compare complete effective profile state and identity-bearing outputs; prove changing/regenerating one owner does not change another. Restore the original same-site identity on return navigation.

Test valid/invalid/malformed/deleted personas, manual override conflicts, a backend insufficient for the requested profile, stale records and unavailable owner information. None may expose host fallback, mutate another record, rotate existing identity or relax guards. Preserve image/video/canvas imports and all pre-existing readback tests.

Run unmodified pinned CreepJS/FingerprintJS with WebGPU enabled and disabled, mode off/on, native controls and multiple supported BrowserForge families. Retain full warnings and provenance. Build, patch replay, package integrity, independent code review and installed Mac reruns precede any completion claim. A failure of privacy or container separation blocks activation/release even if detector warnings disappear.
